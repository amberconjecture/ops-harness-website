# ADR 0026：运营数据只使用 ClickHouse

> 历史决定：2026-10-20 起由 [ADR 0027](0027-typed-tracking-schema.md) 替代。下文描述旧版本表后端，不再作为当前升级操作指南。

状态：已实现，2026-10-18。基于 `common/main` 的服务行为；表结构和统计 SQL 参考 `origin/main` 的 `ff07b05`。

## 决定

官网的运营写入、身份、去重、操作上下文、统计查询与保留期全部使用 ClickHouse。移除服务端 SQLite 建表、升级、事务、查询和维护逻辑，不提供双写、SQLite 回退或后端选择。唯一 SQLite 入口是独立离线补数脚本，只读旧数据库。其他文档、发布、专家、知识库等文件存储保持原职责。

沿用现有十一张 `*_versions` 表的列、排序键、分区和 JSON payload；沿用 `projection_manifest` 和 `published_watermarks`。实体的逻辑最新值仍先按 key/commit_seq 选择完整行，再做保留期、筛选和聚合，避免把历史版本重复计入统计。新代码不再更新 `user_day_versions` 缓存；九类 API 均直接从事实计算，补数保留旧缓存以兼容已有表结构。

新增 `tracking_runtime` 保存一次性接管的 epoch、起始序号和旧未发布区间，新增 `tracking_commits` 保存可重放的整批版本，保留七天。初始化只读取已有发布水位和最大序号，不扫描全表摘要、不做 API 对账、不要求旧 authority/checkpoint 完整。旧直接接管记录中的排除区间一并保留；旧日志、intent 和实体未发布尾部不自动恢复，从其后的新序号继续。

## 写入与恢复

单个官网 Worker 以有界队列串行决定写入。读取只包含本批身份、事件 ID、操作及关联的 pending 终态，不扫描整天事实、不加载全库。纯 TypeScript 决策保留契约校验、时间窗、员工归属、资料更新、事件摘要去重和乱序终态匹配。

写入前在 `analyticsDirectory` 原子保存目标绑定的待提交记录。随后同步写 ClickHouse 整批日志、各实体版本，最后发布水位，全部成功才 ACK。请求结果未知时复用同一序号和同一批内容；重启恢复待提交记录和 CH 未发布日志。管理员读取固定已发布水位，因此中途失败的跨表写入不可见。日志和实体一致性不依赖后台 merge 完成。待提交超过七天时报 `ANALYTICS_PENDING_EXPIRED`，须人工检查，不悄悄确认丢失数据。

沿用 `.tracking.lock` 排斥同目录的服务和 CLI。它不提供跨主机分布式锁；部署必须确保相同目标库只有一个 writer。初次初始化需 DDL 权限；运行时仅需 writer 的 SELECT/INSERT 和 reader 的 SELECT。密码只通过环境提供，错误日志只保留错误码和安全诊断。

## 补数取舍

针对“此前已迁移、回退后 SQLite 又接收新数据”的状态，脚本要求提供带时区的 `--since`，在 SQLite 中只读筛选起点及之后的数据，按主键分批查询目标，只写缺失或变化的值。不走线上事件重放，所以不受 30 天上报窗口约束。保留既有 90/120/400 天数据保留边界；选中后的无效行、孤立 runtime 行和缺失源表计数后跳过；网络或目标写入失败则停止并保留恢复记录。

没有统一创建/更新时间列：事件和去重表按接收时间，事实及操作优先关联接收时间、缺失时用发生时间；操作相关旧事实一并补齐，保留 pending 状态更新。安装按 last_seen，会话按 valid_from，用户按资料时间或选中记录的引用，身份和 runtime 按关联记录。user_day 仅有北京时间日期，包含起点整天；ingestion_health 无时间，跳过累计计数。筛选在源 SQL 中完成，单游标流式读取并分批写入；不为增量选择修改源库或建立索引。

源端仍是停服时的最新状态：既有员工 ID 按 identity 映射，较新的目标资料不倒退；目标独有历史不删除。运行统计不要求逐表行数、哈希、外键完整性或全 API 对账。重跑会重新选择指定时间范围及必要的关联记录，但不重新插入相同逻辑行。补数完成后再启动新服务，不能在新服务持续写入后用旧快照覆盖可变状态。

离线 CLI 通过 package 脚本设置 16 GiB Node 老生代堆上限；仅跨批保存有变化的用户 ID 映射。初始化、查询、写入与恢复默认采用每次请求 5 分钟预算，通过 `--timeout-ms` 调整，整体补数不设截止时间。该覆盖仅限 CLI 内存中的配置，不改变线上服务的 30 秒请求、60 秒查询及 120 秒 Worker 调用预算。保留写入超时后的待提交恢复机制。

操作步骤见 [ClickHouse 单库切换与补数](../runbooks/clickhouse-migration.md)。

## 数据库 DDL 管理

ClickHouse 当前 schema 与编号 migration 统一保存在 [`db/clickhouse`](../../db/README.md)，MySQL 使用独立预留目录。初始化直接读取版本化 SQL，构建同步到 `dist/db`；执行顺序及现有接管行为不变。新增 migration 须同时补充已有库升级路径，不能仅添加 SQL 文件。
