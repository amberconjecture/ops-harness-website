# SQLite 中 user_day 的必要性分析

分析日期：2026-10-19。仅以迁移前 SQLite 实现为依据，不以迁移 ClickHouse 后停写或不读取该表作为理由。

结论：**旧 SQLite 的实际统计功能不依赖 user_day，原 8 列结构不是必需业务存储；它能作为部分指标的预汇总加速表，但旧代码并没有使用这条查询路径。** 当前重设计继续不包含该表，依据改为下述历史代码与隔离验证。不能将这一结论扩大为“日汇总永远没有价值”，也不能在未改造的 SQLite 程序中直接 DROP 表。

## 2. 每个字段保存了什么

只汇总 `user_id IS NOT NULL AND pending=0` 的事实；匿名事件和未匹配终态不进入汇总。已识别的页面访问、后台事件仍可能生成四项指标全为零的行。

| 字段 | 含义及实际计算 |
| --- | --- |
| tenant | 租户 ID |
| day | 事件发生时间对应的北京时间日期 |
| user_id | 内部用户 ID，可与同租户用户资料关联 |
| environment | 环境；同一用户同一天跨环境可以有多行 |
| active | MAX(active)，当天是否至少有一条满足活跃定义的事实，值为 0/1 |
| logins | 仅 auth.login.succeeded 的 operation 去重数；历史 SQL 不包含 installation 前缀 |
| interactions | active=1 的 installation + interaction 去重数 |
| successes | success=1 的 installation + operation 去重数 |

其中四个数值字段全部由 activity_facts 导出，没有独有事实。重传不会再次累加，因为采用受影响日期整日重算。受理与终态跨日、且受理晚到时，会重算两个日期；完成日的成功次数可以增加，但不会因此使完成日 active 变成 1。

事实和汇总都保留 400 天，所以原设计没有利用 user_day 提供更长的历史窗口。若某次事故只剩汇总、事实丢失，剩余汇总仍应随源备份保留并记录缺口；这属于恢复材料，不代表它能替代完整事实。

## 3. 哪些查询能用它，哪些不能

| 统计需求 | 原 user_day 是否足够 | 原因 |
| --- | --- | --- |
| 无版本/平台切片的 DAU | 是 | day 固定、active=1 后按 tenant/user_id 去重 |
| 无版本/平台切片的近 30 天 MAU | 是 | 在 30 天窗口内对 active=1 的 tenant/user_id 去重，不能把每日 DAU 相加 |
| 无版本/平台切片的活跃天数 | 是 | 对用户的 active=1 日期去重；跨环境不能重复计天 |
| 全部环境的 DAU/MAU | 是，但不能相加环境人数 | 表仍保存 user_id，能够跨环境重新去重；跨环境本身不是删除它的理由 |
| 指定 app_version/platform 的任意统计 | 否 | 聚合时已丢失这些维度，不能从汇总倒推 |
| SQLite metricVersion=3 的 loginUsers | 否 | 页面定义为有身份的前台活动用户，不是发生 auth.login.succeeded 的用户 |
| 任意日期范围的精确交互/成功操作去重 | 不能普遍保证 | 只剩每日计数，没有去重键集合；同一键跨日出现时，按日相加会重复 |
| 完整用户列表和排名 | 否 | 缺 firstSeen/lastSeen、功能去重集合、对话/Token/Skill 等，仍需关联事实 |
| 功能、操作明细、采集状态、对话、Skill | 否 | 缺功能/动作/事件明细、匿名事实、安装去重集合、运行用量等 |

三个具体例子：

- 同一用户当天在 development 和 test 都活跃：user_day 有两行，但 DAU 应为 1；正确 COUNT DISTINCT 可以得到 1，因此不能说该表“无法跨环境统计”。
- 用户只访问一个页面：历史总览 loginUsers=1，而该用户 user_day 的 logins=0、active=0。后台用户也可以产生相同零值，不能用“是否存在日汇总行”替代前台用户判定。
- 同一 installation/interaction 在两天各出现一条有效受理事件：每日 interactions 各为 1，求和为 2；历史范围查询按完整交互键去重为 1。现有协议没有禁止这种重复，所以不能无条件求和替代。

## 4. 保留它的收益与成本

潜在收益明确：如果一天有 N 条事件，但只有 U 个用户/环境组合，针对上述可支持指标的查询可以扫描 U 行，而非 N 行。它有成为 DAU/MAU 快速路径的价值；还可成为独立维护的日汇总接口或长期历史方案的起点。

但旧实现没有任何查询读取它，因此原样保留并不会加速已有九类接口，却会在每次有效批次后重扫受影响租户的整天事实、删除并重新写入汇总，增加写入工作和事务时间。不是只更新本批次涉及的用户。

本次没有使用生产规模数据做性能测试，不声称某个具体提速比例或现有查询一定满足延迟目标。若要保留，应先明确哪些请求走汇总、哪些回落事实，补齐登录口径，制定晚到/重放/删除后的重算规则，再以同数据量比较查询耗时、扫描量、写入耗时和维护开销。

## 5. 对设计及迁移的影响

本轮继续不将原 user_day 作为目标必需表，原因是它没有独有数据、SQLite 查询无依赖，且原有字段不能覆盖完整查询需求。保留日汇总作为后续有证据支持的优化选项，不因为缺少版本/平台维度就否认其全部价值。

实施时必须一起移除原 rebuildDays/dirtyDays 和 maintain 中针对 user_day 的路径，保留晚到受理修复 activity_facts.user_id/pending 的逻辑。不能只删表，也不能把 SQLite 同一事务中的事实更新一起删掉。当前交付仅改设计，没有修改线上数据库。

迁移不导入派生汇总到新库，但必须保留源备份，按旧 SQLite 的精确公式在相同 tenant/day 范围重算并对账。不要因为上一版迁移方案称它“停用”就忽略差异；事实缺失、汇总陈旧或口径异常都要区分报告。若未来正式启用新的日汇总结构，从已验证的事实生成，不能直接假定旧计数适配新口径。

## 6. 隔离验证结果

运行 [verify-sqlite-user-day.mjs](verify-sqlite-user-day.mjs)：从 Git 读取上述历史 SQLite 实现及排序常量，转译后只在独立 .runtime 临时目录运行；使用与该历史版本相同的 tracking 契约制品，全部为合成事件。结束删除临时源码、数据库、WAL/SHM，不访问真实数据或 ClickHouse。

```sh
node docs/design/tracking-v2/verify-sqlite-user-day.mjs
```

2026-10-19 在 Node.js 24.14.0 上通过 132 项断言：

- 九类查询 × 六组筛选（全部环境、开发、测试、平台、版本、用户）共 54 个结果，在清空 user_day 后逐项相同；DROP 表后再次逐项相同。
- 实际验证跨日受理晚到后两个日期的汇总更新、重传不重复计数，以及跨环境用户去重。
- 实际验证仅页面访问时 loginUsers=1 但 logins=0，以及两日交互计数之和不等于期间精确去重数。
- DROP 后未改造的历史 ingest 和 maintain 会报缺表；失败 ingest 的事实写入事务回滚。说明删除需要配套代码变更。

这是合成场景的功能验证，配合源代码证明现有查询不依赖该表；不是生产数据完整性或性能压测，也没有证明任何未来新增查询都不需要汇总。
